📅 家族スケジュール＆タスク共有アプリ - 基本設計書 (Draft v2.1)

1. プロダクトの目的

個人のスケジュール・タスク管理と、家族との共有を両立するモバイルアプリケーション。
「時間枠を押さえる予定」と「期限のあるタスク」を明確に区別し、カレンダーやバーチカル、ガントチャートなどの多彩なビューで可視化することで、生活と個人のタスク管理をシームレスに行う。

2. システムアーキテクチャ（全体構成）

フロントエンドとバックエンドの役割を明確に分離したハイブリッド開発環境を採用する。

フロントエンド (Mobile): React Native (Expo SDK 56 / TypeScript) - ホストOS上で開発

バックエンド (API): Java (Spring Boot 3) - Docker内で稼働

データベース: PostgreSQL - Docker内で稼働

認証 (Auth): Firebase Authentication

方針: Firebaseは「パスワード/SNSログインの検証とJWT発行」のみを担当。ユーザーのプロフィールや所属グループなどのビジネスデータはすべてPostgreSQLで管理する。

3. UI/UXの基本方針

単なる月間カレンダーにとどまらず、目的に応じた複数のビューを提供する。

3.1 スペース（空間）の切り替え

「自分専用（個人）」と「共有（家族）」のスペースを切り替えて表示する。

※将来拡張: 初期は「個人」と「家族1つ」の運用を想定するが、裏側の設計は「複数の共有グループ」を作成・所属できる拡張性を持たせておく。

3.2 多彩なビュー（表示形式）

月間カレンダー (TimeTree型): 日別のマス目に予定やタスクのタイトルが並ぶ形式。全体像の把握（予定の点在やタスクの期日を俯瞰）に最適化。

週間/1日表示 (Googleカレンダー型・バーチカル): 縦軸を時間としたタイムライン。「何時から何時まで」という予定（Event）のブロックを視覚的に配置し、空き時間を直感的に把握する。

ガントチャート: 日・週・月単位でスケールを変更できるタイムライン。数日にまたがる予定や、タスクの進捗・期限を帯状に表示し、プロジェクト管理のように使う。

3.3 データの登録（2つの概念の分離）

予定の登録: 「10:00〜12:00」のように明確な時間枠を押さえるもの。

タスクの登録: 「〇日の15:00までに終わらせる」という期限（締切）と、完了ステータスを持つもの。

4. データモデリング（RDB設計の骨格）

スペースの拡張性を担保しつつ、「予定」と「タスク」のドメインをモデリングする。

4.1 スペースとユーザー (将来の複数グループ拡張に対応)

users: ユーザー情報

spaces: 空間（個人用、家族用など）

space_members: どのユーザーがどのスペースに属しているか（多対多）

4.2 コンテンツ (予定とタスクの分離)

events (予定)

space_id (所属スペース)

start_at (開始日時 - 必須)

end_at (終了日時 - 必須)

特徴: バーチカルカレンダーにブロックとして描画される。

tasks (タスク)

space_id (所属スペース)

deadline_at (期限/締切日時 - 必須)

is_completed (完了フラグ)

特徴: カレンダー上にピンポイントの期日として描画される。

⚠️ 要検討事項 (ガントチャートとデータ構造の統合)

UIの切り替え: 月間/週間カレンダーと、ガントチャートの表示切り替え（画面遷移なのか、タブ切り替えなのか、端末の横持ち時のみ表示させるのか等）のUX設計。

データ保持の形式: ガントチャートとして意味を持たせるためには、単純な「予定」と「タスク」だけでなく、タスク間の依存関係（Aが終わるまでBは開始できない等）や進捗率、あるいは「数日間にまたがるタスクの表現」をDB上でどう持たせるか、今後の詳細設計で詰める必要がある。

5. 予定・タスクの通知（要検討）

予定の開始前リマインドや、タスクの期限間近のアラート。

家族スペースに新しい予定・タスクが追加された際のプッシュ通知機能。

6. バックエンド設計思想

過度な複雑化を避け、標準的で保守性の高いアーキテクチャを採用する。

アーキテクチャ: クリーンアーキテクチャ ＋ DDD (ドメイン駆動設計)

基本方針: CQRS/ES等の複雑なパターンは採用せず、普遍的なUseCaseを中心としたレイヤードアーキテクチャとする。

Presentation: APIエンドポイント (Controller)

UseCase: アプリケーションのユースケース進行

Domain: Event や Task といったエンティティとビジネスルール（例：終了日時は開始日時より後など）

Infrastructure: PostgreSQLへの永続化 (Repository実装)
